# Capital Ship Production Source Trace

## Purpose

This document preserves the verified source trace, the implemented capital-ship role slice, and the remaining work required for complete strategic-production parity.

## Bottom Line

- The manufacturing throughput calculation is correct and remains unchanged.
- The original selects a strategic capability shortage first, ranks compatible products with a role-specific metric, and accepts the first affordable candidate.
- The implemented slice applies that role-specific product selection to the repo's existing fleet-demand pipeline for general combat, troop transport, and bombardment shortages.
- The implemented selector derives compatibility from ship capabilities, applies the verified maintenance budget, and uses the injected random stream for equal-metric candidates.
- Planet-destroying ships remain excluded until their separate strategy lane is implemented.
- Capital ships are ordered for a manufacturing system. They are not manufactured directly into a destination fleet.
- Fleet creation, consolidation, loading, and movement are a separate downstream AI flow and must not be inferred inside production planning.
- Product roles are derived from ship capabilities. The implementation must not hardcode ship TypeIDs or ship names.

## Verified Manufacturing Throughput

The original has one production queue for each manufacturing family at a planet. Multiple matching facilities do not create independent parallel queues. Every active facility contributes throughput to the same queue.

The original aggregate rate is built by summing `100 / ProcessRate` for every active matching facility:

- `FUN_00527b20_get_all_facility_processing_rate.c`
- `FUN_00527ef0_get_build_completion_days.c`

The completion estimate divides remaining work by the aggregate rate and rounds up. The manual independently states that two matching facilities double production speed and three triple it.

The repo already follows this model:

- `Assets/Scripts/Systems/ManufacturingSystem.cs`
- `EstimateProductionTicks` sums `_productionRateScale / facility.GetProcessRate()`.
- Production ticks collect ready points from all matching facilities and apply them to the shared queue.

Do not replace this with one queue per facility.

- Placement orders planets by the current count of that building type ascending.

That placement policy is not established by the original production trace. The original type-1 strategy path creates local/system shortage records and resolves eligible system contexts. A source-faithful building-placement change requires a separate complete trace through the type-1 issue-row writer, consumer, scheduler, and emitted building command.

Do not remove building scoring. Building work should continue to separate:

1. which facility role is needed
2. which unlocked facility satisfies that role
3. which planet should receive it

The current global planets-per-facility rule must not be presented as original behavior.

2. `FUN_004c7f90` enters the production phase.
3. `FUN_004c9950_choose_production_shortage_request_family` selects a capability shortage and its ranking metric.

This closes the required writer, reader, scheduler, finalize, and gameplay-commit chain for capital-ship production.

## Capability Shortage Selection

`FUN_004c9950_choose_production_shortage_request_family` scans existing strategic issue records and counts six capability lanes. It ignores a lane when that lane is already marked pending. Its nested comparisons choose an absent or least-represented lane.

This is not a raw count of living ships and is not a count of ship names. It balances strategic role/request records.

The source comparison and tie ordering must be preserved. Do not replace the nested source ordering with a generic `OrderBy(count)` unless tests prove identical behavior for every tie combination.

## Candidate Query and Budget Gate

The product query path is:

- Wrapper: `FUN_0041aa20.c`
- Product selection: `FUN_0042ddc0.c`
- Product comparison: `FUN_0041ba00_compare_and_decide.c`

`FUN_004c9c80` calls the ship-family query with:

- product family `0x28`
- the selected required-capability value
- the selected role-specific metric
- ordering mode `1`

The query filters products with the equivalent of:

```text
(productCapabilities & requiredCapabilities) == requiredCapabilities
```

It returns an ordered candidate collection. `FUN_004c9c80` walks that collection and selects the first candidate whose required value/cost is less than or equal to the budget. If no candidate is affordable, it marks the selected role pending.

This establishes the important ordering:

1. select the needed role
2. filter to compatible products
3. rank with the role-specific metric
4. apply affordability as a hard acceptance gate

Do not subtract construction cost and maintenance cost from every ship's universal utility score. Cost participates where the selected source metric explicitly measures efficiency, and otherwise acts as the budget ceiling.

The budget function is `FUN_004cb590.c`. Its exact source arithmetic is:

```text
budget = (((strategyScale * managerValueAt0x184) / 100) * 90) / 100
         - managerValueAt0x24c

if (managerValueAt0x184 - managerValueAt0x188 < budget)
    budget = 0
```

Before implementing the budget formula, map those manager fields through their writers and consumers. Do not assign repo-native names to the offsets from intuition.

## Production Context and Completion

The original production order is system-scoped.

### Context selection

- `FUN_004c9670.c` chooses an eligible live manufacturing/system context from the type-11 candidate list.
- When no suitable candidate is available, it falls back through the manager's primary/home system path.
- `FUN_004ca030.c` queries and repopulates eligible systems when the candidate list is empty.

### Emitted package

`FUN_004cae00.c` emits strategy package `0x211`. The package carries:

- faction/side
- manufacturing or system context ID
- selected product ID
- quantity

It does not carry a destination Fleet ID.

The same command shape is consumed through both the human strategy-command path and the computer strategy-worker path:

- `FUN_00486400_handle_strategy_command.c`
- `FUN_00484f90.c`
- `FUN_00489ee0.c`

Manufacturing completion flows through:

- `FUN_0052ab20.c`
- `FUN_0052aff0.c`
- `FUN_0052b090.c`

The completed ship is created and attached through the producing context. Production does not create an empty destination fleet and does not bind the unfinished ship to a fleet.

## Implemented Slice And Remaining Divergence

`AIProductionDemandGenerator` assigns one of three role shortages to a fleet demand:

- troop transport when regiment capacity is short
- general combat when projected combat strength is short
- bombardment when bombardment strength is short

`AIProductionPlanner` filters unlocked capital ships by the selected role, ranks them with that role's metric, applies the capital maintenance budget as a hard affordability gate, and resolves equal metrics through the injected random provider. It excludes gravity-well ships from the current general and transport lanes and excludes configured planet-destroying ships from every normal lane.

The fleet-deficit selector is a bounded integration with the current AI pipeline. It does not replace the original type-11 least-represented role records, pending flags, anti-fighter lane, carrier lane, gravity-well lane, or Death Star lane.

### Direct-to-fleet manufacturing

`Assets/Scripts/AI/Proposals/AIManufactureProposal.cs` currently:

- enqueues reinforcement ships directly to a Fleet destination
- creates an empty battle fleet for `FleetSeedCapitalShip`
- enqueues the first unfinished capital ship directly to that new fleet

The original production package has no fleet destination. This behavior must be removed from production when the source-shaped flow is implemented.

### Producer selection

`AIProductionPlanner.FindProducerPlanets` currently sorts producers by distance to the demand destination and then by production rate.

The source uses a strategy-maintained eligible system list plus fallback context selection. Do not preserve nearest-destination producer selection as a silent fallback in the source-parity path.

3. Preserve its tie ordering.

### Stage 3: Candidate ranking and affordability

1. Filter unlocked products by the selected source capability mask.

4. Walk candidates in order and accept the first affordable product.

1. Resolve an eligible producing system using the translated type-11 candidate path.

4. Let normal manufacturing completion attach the ship at the producing system.

### Stage 5: Separate fleet organization

1. Trace the original selector that consumes available completed ships at systems.
2. Trace fleet creation, ship grouping, troop and fighter loading, and movement assignment end to end.
3. Bind completed ships to fleets only through that proven downstream path.
4. Do not invent nearest-fleet, weakest-fleet, empty-fleet, or destination-fleet heuristics inside manufacturing.
